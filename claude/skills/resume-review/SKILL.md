# 職務経歴書レビュー（resume-review）

職務経歴書を **プロジェクト単位** でレビューし、各プロジェクトを7観点で採点して、
欠落・弱点を可視化し、**具体的な書き換え案（before→after）** まで出す。

## 大原則（最優先・厳守）

1. **数値を捏造しない。** 「障害◯件減」「◯%短縮」などの数字は、必ず本人が持っているデータ。
   不足している箇所は `[要ヒアリング: ...]` と明示し、**プロセス末尾でまとめて質問する**。
   推測値を書き込んではいけない。`約`を付けても捏造は捏造。
2. **「チーム情報」と「自分 vs チームの線引き」を最優先で引き出す。**
   これは採用側が最も見る点で、**指名・書類通過の最大の分岐点**。実力が同等でも、ここが
   曖昧だと「この成果のうち、この人は何をした人か」が読めず選ばれない。全プロジェクトで
   必ず ①チーム規模（何人）②役割構成（リーダー/レビュアー/PM/インフラ等が何人）
   ③本人のポジションと決定権の範囲 ④「自分が手を動かした/設計した部分」と「チームがやった部分」
   の区別 を明示させる。原文に無ければ `[要ヒアリング]` で必ず回収する（捏造は禁止）。
3. **抽象アドバイス禁止。** 「数字を足しましょう」で終わらせない。必ず before→after の文面で示す。
4. **本人の事実を勝手に盛らない。** 役割（リーダー/メンバー）・体制・期間は原文を尊重する。
   表現を強くするのは可。事実を変えるのは不可。
5. **トーンは中立・強く。** 謙遜表現（「たまたま」「素養を育んだ」「〜なだけ」）は削る提案をする。

## 手順

### 0. 入力を取得
- PDF / Word / Markdown / 直貼りテキストのいずれか。PDFは Read で読む。
- ターゲット職種・志望の方向性を確認（自己PRや本人の発言から推定。不明なら後でヒアリング）。
  → これがレビューの基準線になる（「誰に向けた書類か」）。

### 1. プロジェクトを分解
各社・各プロジェクトを1ブロックとして抽出する。

### 2. 各プロジェクトを7観点で採点
各観点を **✅充足 / △弱い / ❌欠落** で評価し、表で示す。

| # | 観点 | 見るポイント |
|---|------|------------|
| ① | どんなサービス・システムか | ドメイン・規模感（ユーザー数/リクエスト数/データ量/プロダクト数/稼働年数）が分かるか |
| ② | 自分は何を担当したか（**最重要・大原則2**） | チーム規模・役割構成が書かれ、その中で**自分のポジションと責務**が具体か。**「自分がやったこと」と「チームがやったこと」が区別**できるか。連携相手（PdM/レビュー担当等）まで書けているか。ここが△以下なら総評で最優先の改善点として挙げる |
| ③ | どんな技術を用いたか | 言語・FW・インフラ・監視ツールが**何にどう使われたか**まで紐づくか（羅列で終わってないか） |
| ④ | どんな機能を開発したか | 機能の**目的・ビジネス価値**（何のため・誰のため）が言えているか |
| ⑤ | どんな課題に取り組んだか | 課題の**深さと背景**（なぜ難しいか）が具体か。「課題が多かった」で止まってないか |
| ⑥ | どんな工夫をしたか | 取りうる選択肢の中で**なぜその手段を選んだか**（意思決定・トレードオフ）が見えるか |
| ⑦ | どんな成果を出したか | **定量** が入っているか（件数/%/時間/頻度/金額）。なければ `[要ヒアリング]` |

### 3. 全体監査（7観点の外側）
プロジェクト単位では拾えない減点要素を一括チェック：

- **表記ゆれ**：`.NET`/`NET`、`SLO`/`slo`、`SRE`/`sre`、`Git`/`git`、`API`/`api`、`IIS`、`Azure Monitor` 等の固有名詞の正確さ・大小文字。
- **謙遜・自己卑下**：「たまたま」「〜なだけ」「素養」「杜撰だった」→ 中立で強い表現へ。
- **結果の欠落**：`結果` ブロックが無い／定性で終わっているプロジェクト。
- **スキル欄 vs 実務の乖離**：職務経歴で使った言語/技術がスキル欄に無い、または逆。
- **自己PRの願望化**：「〜したいです」中心になっていないか。実績ベース＋意志、の順へ。
- **キャリアの一貫性**：各プロジェクトがターゲット職種の物語に向いているか。
- **日付・体裁の不整合**：期間の矛盾、誤記、リンク切れ。

### 3.5 スカウト媒体特有チェック（転職ドラフト等のスカウト型のみ）
一般の職務経歴書レビューに加え、スカウト媒体（企業が閲覧して指名/オファーする型）では
以下も見る。汎用の書類提出では該当しないので、媒体が分かる場合のみ適用：

- **プロフィール完成度**：未入力欄（学歴・語学・希望年収等）が指名率を直接下げる
  （転職ドラフトは完成度100%で指名数 約1.3倍と公表）。埋めるべき穴を挙げる。
- **公開/非公開設定**：職経を非公開にしていると検索・閲覧されない。公開推奨。
- **アウトプットの見せ方**：GitHub/Zenn/登壇資料は「何を・なぜ見てほしいか」を一文で。
  「たまに書いてます」等の軽い表現は具体化。
- **意欲・志向シグナル**：転職意欲の設定や希望条件が企業の本気度に影響する点を（押し付けず）指摘。
- **リード/マネジメント経験の申告漏れ**：勉強会主導・移行リード・SLO立ち上げ等は
  「マネジメント経験なし」ではなく技術リード実績として申告できる。過小申告を拾う。
- **ブランドシグナル**：著名企業/プロダクト名は強い加点。出す/匿名は本人判断だが選択肢として提示。

### 4. 改善案を before→after で提示
各プロジェクトについて、書き換え案を出す。平坦な段落にせず、**読み手が流し読みできる
見出し付きの構造**にする（採用側は密な文章を読まない）。次の型に組み替える：

```
【概要】1〜2行（ドメイン・規模感）
【チーム情報】規模・役割構成・自分のポジション（大原則2。無ければ[要ヒアリング]）
【開発・実装A：◯◯（自分が主担当/リード等を明示）】
  - どんな機能か（目的・ビジネス価値）
  - 課題（なぜ難しいか）
  - 打ち手（なぜその手段か。**自分がやった部分を明示**）
  - 成果（定量。無ければ[要ヒアリング]）
【開発・実装B：…】同上
```

課題→行動→結果（STAR）は各「開発・実装単位」の中で満たす。単発の小さな案件は
A/B分割せず1ブロックでよいが、その場合も【チーム情報】と自分の担当明示は必須。
`[要ヒアリング: 環境構築時間]` のように、本人に埋めてほしい数値はプレースホルダで残す。

### 5. 不足データをまとめてヒアリング
`[要ヒアリング]` を箇条書きで集約し、本人に質問する。回答が来たら、その内容で文面を確定させる。
必ず質問対象に含める2系統：
- **チーム情報（大原則2・最優先）**：各プロジェクトの ①チーム規模 ②役割構成
  ③本人のポジション/決定権 ④自分の担当範囲とチームの担当範囲の線引き。
- **定量成果**：開発環境構築の短縮時間、削減工数、想定リクエスト/データ規模、削減コスト%、
  障害件数の増減、デプロイ頻度など。

### 6. 反映方法を提示
1. 元データ（Word/Markdown等）があれば直接編集
2. 反映済みの完成版テキストを書き起こし
3. 特定プロジェクトだけ深掘り

## 出力フォーマット

```
## 総評（3行以内）
…

## プロジェクト別レビュー
### 〔プロジェクト名〕
| 観点 | ①|②|③|④|⑤|⑥|⑦ |
| 評価 | ✅|△|❌|… |
**弱点**：…（②チーム情報/自分の担当が△❌なら最優先で明記）
**before**：（原文）
**after**：（【概要】→【チーム情報】→【開発・実装A/B…】の構造で。数値・チーム情報は[要ヒアリング]で残す）

## 全体監査
- 表記ゆれ：…
- 謙遜表現：…
- スキル乖離：…
- 自己PR：…
- 一貫性：…

## スカウト媒体チェック（該当時のみ）
- 完成度/未入力欄：…
- 公開設定：…
- アウトプットの見せ方：…
- リード/マネジメント申告漏れ：…

## 要ヒアリング
- [ ] チーム情報：〔プロジェクト名〕規模/役割構成/自分のポジション/担当範囲の線引き
- [ ] 定量：…
```

## やってはいけないこと
- 数字をでっち上げる（最大のNG）。
- 観点を点数化するだけで書き換え案を出さない。
- 本人が書いていない経歴・役割を追加する。
- 全プロジェクトを一律のテンプレ文に置き換えて個性を消す。
